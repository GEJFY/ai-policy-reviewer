class CheckItem(BaseModel):

#### チェックカテゴリ定義
```python
class CheckCategory(str, Enum):
    TERMINOLOGY = "用語統一"          # 用語の一貫性チェック
    GRAMMAR = "文法・表現"            # 文法・日本語表現のチェック
    STRUCTURE = "構成・体裁"          # 文書構造のチェック
    COMPLIANCE = "法令・コンプライアンス" # 法的要件のチェック
    CONSISTENCY = "整合性"            # 他規程との整合性チェック
    SECURITY = "セキュリティ"         # 情報セキュリティ観点
    OPERATIONAL = "実務適合性"        # 実務上の実現可能性
```

#### 標準チェック項目一覧

| ID | name | category | severity | description |
|----|------|----------|----------|-------------|
| 1 | 用語統一チェック | TERMINOLOGY | HIGH | 社内用語辞書に登録された正式用語との不一致を検出 |

| 3 | 責任主体明確化 | STRUCTURE | HIGH | 「誰が」「いつまでに」「何を」が明確かチェック |

| 5 | 他規程参照チェック | CONSISTENCY | MEDIUM | 参照している他規程との整合性を確認 |
| 6 | 機密情報取扱 | SECURITY | HIGH | 機密情報の取扱いルールの適切性を確認 |
| 7 | 承認フロー妥当性 | OPERATIONAL | MEDIUM | 承認権限・フローが実務上妥当かを確認 |

## 2. AIレビュー機能のプロンプト設計

### 2.1 システムプロンプト（共通）

```markdown
# System Prompt: 規程レビューアシスタント

あなたは企業の内部統制・コンプライアンス部門で活動する規程レビューの専門家です。
以下の原則に従って、規程文書をレビューしてください。

## レビューの基本原則
1. **客観性**: 感情や主観を排し、事実に基づいて指摘する
2. **具体性**: 問題箇所を明確に特定し、具体的な改善案を提示する
3. **優先度付け**: 重要度（HIGH/MEDIUM/LOW）を明確にする
4. **根拠明示**: 指摘の根拠となるルール・基準を明示する

## 出力形式
指摘事項は以下のJSON形式で出力してください：
```json
{
  "findings": [
    {
      "id": "連番",
      "location": "該当箇所（条項番号・行番号）",
      "original_text": "問題のある原文",
      "issue_type": "問題種別",
      "severity": "HIGH|MEDIUM|LOW",
      "description": "問題の説明",
      "suggestion": "改善提案",
      "rationale": "指摘根拠"
    }
  ],
  "summary": {
    "total_findings": "総指摘数",
    "high_count": "HIGH件数",
    "medium_count": "MEDIUM件数",
    "low_count": "LOW件数"
  }
}
```

## 制約事項
- 規程の本質的な意図を損なう変更は提案しない
- 法的判断を要する事項は「法務部門との確認を推奨」と注記する
- 業務フローの大幅な変更を伴う提案は慎重に行う
```

### 2.2 チェック項目別プロンプトテンプレート

#### 2.2.1 用語統一チェック (TERMINOLOGY)

```markdown
# 用語統一チェック

## チェック対象
以下の規程文書の用語使用を確認してください。

## 参照する社内用語辞書
{terms_context}

## チェック観点
1. **正式用語との不一致**: 用語辞書に登録された正式用語と異なる表記を検出
2. **表記ゆれ**: 同一文書内での表記の不統一を検出
3. **未定義用語**: 用語辞書に未登録の専門用語・略語を報告

## レビュー対象文書
{document_content}

## 指示
上記の観点で文書をレビューし、用語に関する指摘事項を抽出してください。
各指摘には、該当箇所・問題内容・推奨される表記を含めてください。
```

#### 2.2.2 曖昧表現チェック (GRAMMAR)

```markdown
# 曖昧表現チェック

## チェック対象
以下の規程文書から、実務上の解釈に曖昧さが生じる表現を検出してください。

## 検出対象パターン
1. **範囲が不明確な表現**
   - 「等」「など」「その他」「原則として」「基本的に」

2. **程度が不明確な表現**
   - 「適宜」「必要に応じて」「速やかに」「遅滞なく」「相当の」

3. **主体が不明確な表現**
   - 受動態での責任主体不明（「〜される」「〜が行われる」）
   - 「関係部門」「担当者」等の曖昧な主体指定

4. **条件が不明確な表現**
   - 「場合によっては」「状況に応じて」「重要な場合」

## 記載ルール
{writing_rules_context}

## レビュー対象文書
{document_content}

## 指示
各曖昧表現について：
- 該当箇所を特定
- なぜ曖昧か（解釈の幅を具体的に説明）
- 明確化のための改善案を提示
- ただし「適切な柔軟性」として意図的に曖昧にしている可能性がある箇所は、
  その旨を注記した上で報告
```

#### 2.2.3 責任主体明確化チェック (STRUCTURE)

```markdown
# 責任主体明確化チェック

## チェック対象
規程の各条項について、以下の5W1Hが明確に定義されているか確認してください。

## 確認観点
1. **Who（誰が）**: 責任主体・実行主体が明確か
2. **When（いつ）**: 実施時期・期限が具体的か
3. **What（何を）**: 対象・範囲が特定されているか
4. **How（どのように）**: 手順・方法が示されているか
5. **Where（どこで）**: 適用範囲・場所が明確か
6. **承認権限**: 意思決定・承認の権限者が明確か

## レビュー対象文書
{document_content}

## 指示
各条項について5W1Hの観点でレビューし、不明確な箇所を指摘してください。
特に以下は重点的にチェック：
- 「○○部門」ではなく具体的な部署名・役職が必要な箇所
- 「速やかに」ではなく具体的な期日（○営業日以内等）が必要な箇所
- 例外処理・エスカレーションのルートが不明確な箇所
```

# 法令参照チェック

## チェック対象

## 確認観点

2. **条文番号の正確性**: 参照条文が正しいか
3. **法改正への対応**: 最新の法令内容と整合しているか
4. **引用形式の統一**: 引用形式が統一されているか

## 主要な参照法令（コンテキスト）
{legal_context}

{document_content}

## 指示

#### 2.2.7 実務適合性チェック (OPERATIONAL)

```markdown
# 実務適合性チェック

## チェック対象
規程の内容が実務上実行可能かを確認してください。

## 確認観点
1. **承認フローの妥当性**
   - 承認階層が適切か（過剰な階層がないか）
   - 承認者不在時の代行ルールがあるか
   - 緊急時の例外処理が定義されているか

2. **期限の現実性**

   - 繁忙期等を考慮した柔軟性があるか

3. **システム対応**
   - 規程の要求事項は現行システムで対応可能か
   - 手作業が必要な箇所は明確か

4. **リソース要件**
   - 必要な人員・スキルは現実的か
   - コスト面で実行可能か

## レビュー対象文書
{document_content}

## 指示
実務担当者の視点から、規程の実行可能性を評価してください。
実務上の困難が予想される箇所には、具体的な改善提案を含めてください。

### 3.2 プロンプト組み立て実装例

```python
# backend/app/services/prompt_builder.py

class PromptBuilder:
    """チェック項目に応じたプロンプトを構築するサービス"""

    SYSTEM_PROMPT = """あなたは企業の内部統制・コンプライアンス部門で活動する
規程レビューの専門家です。..."""  # 2.1のシステムプロンプト

    TEMPLATES = {
        CheckCategory.TERMINOLOGY: """# 用語統一チェック
## 参照する社内用語辞書
{terms_context}
## レビュー対象文書
{document_content}
...""",
        CheckCategory.GRAMMAR: """# 曖昧表現チェック
...""",
        # ... 他カテゴリ
    }

    async def build_prompt(
        self,
        check_item: CheckItem,
        document_chunks: list[str],
        terms: list[Term],
        writing_rules: list[WritingRule],
        related_docs: list[Document] | None = None
    ) -> list[dict]:
        """プロンプトを構築"""

        # コンテキスト文字列の構築
        terms_context = self._format_terms(terms)
        rules_context = self._format_rules(writing_rules)
        doc_content = "\n\n".join(document_chunks)

        # テンプレートにコンテキストを埋め込み
        template = self.TEMPLATES.get(
            check_item.category,
            check_item.prompt_template  # カスタムテンプレート
        )

        user_prompt = template.format(
            terms_context=terms_context,
            writing_rules_context=rules_context,
            document_content=doc_content,
            related_documents_context=self._format_related_docs(related_docs)
        )

        return [
            {"role": "system", "content": self.SYSTEM_PROMPT},
            {"role": "user", "content": user_prompt}
        ]

    def _format_terms(self, terms: list[Term]) -> str:
        """用語リストをMarkdown表形式に変換"""
        lines = ["| 正式用語 | 別名 | 定義 |", "|---|---|---|"]
        for t in terms:
            aliases = ", ".join(t.aliases) if t.aliases else "-"
            lines.append(f"| {t.term} | {aliases} | {t.definition} |")
        return "\n".join(lines)
```

## 5. 承認ワークフロー

### 5.1 承認ステータス遷移

```
PENDING（保留）
    │
    ├──[承認]──► APPROVED（承認）──► 文書に反映
    │
    ├──[却下]──► REJECTED（却下）──► 対応不要
    │
    └──[保留]──► DEFERRED（延期）──► 次回検討
```

### 5.2 一括承認機能

```
POST /api/v1/reviews/{review_id}/findings/bulk-approve
```

**リクエスト**
```json
{
  "finding_ids": [1, 2, 3, 5, 8],
  "action": "APPROVE",
  "comment": "軽微な用語修正のため一括承認"
}
```

## 付録: プロンプトチューニングガイドライン

### Temperature設定

| 用途 | Temperature | 理由 |
|------|-------------|------|
| レビュー実行 | 0.2-0.3 | 一貫性・再現性重視 |
| 変更提案生成 | 0.3-0.5 | 適度な創造性を許容 |
| 比較分析 | 0.1-0.2 | 正確性最重視 |

### トークン上限

| 処理 | Max Tokens | 理由 |
|------|------------|------|
| レビュー結果 | 4000 | 複数指摘を含むため |
| 変更提案 | 1000 | 単一提案のため |
| 比較分析 | 2000 | 変更一覧のため |

### 評価指標

- **精度**: 誤検出率（False Positive）を10%以下に
- **再現率**: 重要な問題の見落とし率を5%以下に
- **一貫性**: 同一文書への再実行で90%以上の指摘一致率
